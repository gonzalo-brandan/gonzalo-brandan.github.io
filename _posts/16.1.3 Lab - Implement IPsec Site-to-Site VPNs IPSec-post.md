In this lab i will establish a site-to-site IPsec VPN tunnel between R1 to R3 via R2. R2 is the ISP router, and it will have no knowledge of the VPN (this meaning that R2 simply forwards the encrypted traffic between R1 and R3 without participating in the VPN negotiation, key exchange, or encryption/decryption process).

VPN negotiation is the process where R1 and R3 agree on parameters (like encryption algorithms and lifetimes) to set up the tunnel. Key exchange (for example via IKE) securely generates shared keys, which are then used for encrypting traffic at the sender and decrypting it at the receiver. IPsec works at the network layer (OSI 3). 

IPsec is an open framework that allos for the exchange of security protocols as new technologies, and encryption algorithms as they are developed.

There are two central configuration elements in the implementation of an IPsec VPN:
- Implement Internet Key Exchange (IKE) parameters (how the two devices **agree on keys and set up** the VPN.)
- Implement IPsec parameters (how the actual **data is encrypted and protected** after the tunnel is up.)

### Step 1: On R1 and R3, implement Internet Key Exchange (IKE) parameters

In this step, I will enable IKE policies on R1 and R3. IKE Phase 1 defines the key exchange method used to exchange and validate IKE policies between peers. In IKE Phase 2, the peers exchange and match IPsec policies for authentication and encryption of data traffic.

So:
- **Phase 1 = “secure handshake channel”** (IKE‑SA) between R1 and R3.
   - **Phase 2 = “data‑protection channel”** (IPsec‑SA) that encrypts the real traffic.

IKE must be enabled for IPsec to function. IKE is enabled by default on IOS images with cryptographic feature sets. If disabled, it can be enabled with the command **crypto isakmp enable**. If that command produces and error, the device must be upgraded.

For IKE Phase 1, you define an ISAKMP policy with authentication, encryption, and hash algorithms. When both routers accept the ISAKMP security association (SA), Phase 1 is complete.

A security association (SA) is a agreement between two devices that defines how traffic is encrypted, authenticated, and protected in an IPsec VPN.

## Step 1 Create a custom ISAKMP policy

In order to create a custom ISAKMP policy, I will enter ISAKMP configuration mode using the command **crypto isakmp policy** *number* in global configuration mode. The policy number uniquely idefntifies the IKE (**the key‑exchange and negotiation protocol**) policy and assigns a priority to the policy, where 1 is the highest priority. So the router will try **ISAKMP policy 1 first**, then 2, 3, etc., when negotiating IKE with the other device.

The parameters explained:
- **Encryption algorithm**  
Determines how **confidential** (secret) the control channel is; it decides how the negotiation messages are encrypted.
    
- **Hash algorithm**  
The hash algorithm controls data integrity, ensuring that the data received from a peer has
not been tampered with in transit
    
- **Authentication type**  
Ensures the packets really come from the **intended peer** (e.g. via pre‑shared key or certificate) and not from an attacker.
    
- **Diffie‑Hellman group**  
Is used to **generate a shared secret key** between the peers in a way that the key itself is never sent over the network, so it stays secure.

## Configuring the pre-shared keys

Because the pre-shared keys are used as the authentication method in the IKE policy, a key must be configured on each router that points to the other VPN endpoint. These keys must match for authentication to be successfull.

The command to do this is **crypto isakmp key *key-string* address *ip-address***. The IP address in this case is the global IP address of the remote peer, which is the outside interface of it.

Also the ip-address parameter can be assigned **0.0.0.0 0.0.0.0** to allow a match against any peer. (you use it when the exact peer IP is unknown, dynamic, or you want a single policy to cover many peers.)

## Configuring the IPsec transform set

The IPsec transform set is another crypto configuration parameter that routers negotiate to form a security association. To create an IPsec transform set, the command to use is **crypto ipsec transform-set** *transform-set-name transform1 \[transform2\[transform3]]*.

An IPsec transform set is a named group of settings that define how the VPN traffic is protected, such as the encryption algorithm (confidentiality), hash algorithm (integrity), and tunnel mode. R1 and R3 must agree on the same transform set so they can build matching IPsec security associations for the tunnel.

The ISAKMP configuration I configured on Step 1 protects the _control messages_ between the routers (IKE Phase 1), but the IPsec transform set is needed to define how the _actual user data_ is encrypted and authenticated inside the VPN tunnel (IPsec Phase 2).

On R1 and R3 I will create a transform set with the name S2S-VPN and use ? to see which parameters are available.

![[Pasted image 20260522131707.png]]

This whole list shows the **IPsec transform options** you can use inside a `crypto ipsec transform-set` on Cisco routers:

- **`ah-xxx` (e.g., `ah-sha-hmac`)**  
    Uses the **Authentication Header (AH)** protocol, which provides **authentication/integrity only** (no encryption).
    
- **`esp-xxx` (e.g., `esp-aes`, `esp-sha-hmac`)**  
    Uses the **Encapsulating Security Payload (ESP)** protocol, which can provide **encryption + integrity**, or just integrity.
    
- **`xxx-hmac` (e.g., `esp-sha-hmac`)**  
    Means **HMAC** (Hash‑based Message Authentication Code): a way to verify that the packet has not been changed and comes from the right peer, using a hash plus a secret key.
    
- **`esp-aes`, `esp-3des`, `esp-des`, etc.**  
    Are different **encryption algorithms** (AES‑256, AES‑192, 3DES, DES) that decide how the data is encrypted inside the tunnel.

```
R1, R3 (config)# crypto ipsec transform-set S2S-VPN esp-aes 256 esp-sha256-hmac
```

**Note**: the transforms inside the transform set do **not** have to match the ISAKMP policy; they can be stronger, weaker, or different, as long as both peers agree on the IPsec transforms.

## Step 4: On R1 and R3, define interesting traffic.

It is necessary to define interesting traffic that will tell the router to enable an IPsec VPN with other VPN peer. I will do this by using an extended ACL to tell the router which traffic to encrypt. A packet that is denied by one of these ACL is not dropped but is instead forwarded to its destination unencrypted. 

In this scenario, from the perspective of R1, the traffic I want to encrypt is traffic going from the R1 LANs to the R3 LANs, or vice versa from the perspective of R3. These ACL are used outbound on the VPN endpoint interfaces and must mirror each other.

If the ACLs are not mirrored, the tunnel may come up, but the traffic you expect to encrypt will not match the policy and will bypass the IPsec tunnel.

## Step 5: Create and apply a crypto map

A crypto map assoaciates traffic that matches an ACL to a peer and various IKE and IPsec settings. After the crypto map is created, it can be applied to one or more interfaces. The interfaces that it is applied to should be the ones facing the IPsec peer.

To create a crypto map, use the **crypto map** *name sequence-number type* command in global configuration mode.

## Takeaway

Overall, this lab helped me understand how an IPsec site‑to‑site VPN is built in layers: first IKE sets up a secure channel, then IPsec protects the actual data, while the ISP router in the middle simply forwards encrypted packets without any involvement.

The key takeaway is that both IKE and IPsec parameters must match on the peers, and the “interesting traffic” ACLs really do need to be mirrored so the routers agree on what gets encrypted. Seeing the tunnel come up and the SAs appear after a successful ping was a satisfying confirmation that the pieces are finally working together.
